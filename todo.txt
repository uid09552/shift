### 6. Rotation patterns as proposed in ui-proposals.md

Hospitals plan in rhythms: *early, early, late, late, night, night, off, off*.
Here, every recurring commitment is entered one assignment at a time.

A pattern is a named sequence of shift slots plus a cycle length. The page: pick
a pattern, pick people, pick a start date and a horizon, preview the grid it
would produce, write it. The writes are ordinary
`employee_shift_assignments` — the table and the import endpoint already exist —
so this is a generator and a preview, not a new subsystem.

DONE. Planner → Rotations: write a pattern ("F F S S N - - -", checked against
the planner's rules as you type), pick people, period and a stagger, preview the
exact grid, write it. Writes ordinary employee_shift_assignments — a day off is
an assignment without a shift (migration 27). The planner now actually reads
them (it ignored fixed assignments before) and keeps them ahead of every other
goal; any a rule forbids is named in the result instead of making the plan
infeasible. API: /rotation-patterns (+ /apply with dry_run), GET
/shift-assignments, POST /shift-assignments/clear. The agent's plan check flags
fixed assignments a proposal does not keep. Removed from docs/ui-proposals.md.
